## Scope and verdict

Repository: `knarayanareddy/cognition`, pinned to `36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7`. This is an implementation-stage MVP, not a production assessment. The sampled backend exposes an OAuth callback that creates a fresh user ID, while consent and deletion use a fixed development ID. That is a confirmed source-level identity mismatch and a blocker to safely handling real users until the boundary is redesigned and verified. It does not establish deployed use or prove where other application data is written.

The frontend pages, other routers/services, database schema, deployed configuration, secret consumption, CI execution and actual authorization behavior were not inspected. Runtime, tests, OAuth and provider calls were **not run**. Findings are static observations or conditional risks, not certification. See the inventory for the precise sample.

## Findings ledger

### COG-001 — Shared placeholder identity conflicts with OAuth identity
**High; confirmed static.** [`consent.py:33–36`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/consent.py#L33-L36) says “Placeholder: returns a fixed user_id for development”; [`consent.py:40–48`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/consent.py#L40-L48) and [`:66–95`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/consent.py#L66-L95) query and update consent against that dependency. [`user_data.py:25–27`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/user_data.py#L25-L27) supplies the same unauthenticated fixed ID; [`:30–59`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/user_data.py#L30-L59) deletes scores, interventions, signal snapshots, consent and tokens filtered by it. Conversely, [`auth.py:97–115`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/auth.py#L97-L115) uses `user_id = uuid.uuid4()` on each callback and saves the token under that new ID.

Consequently these consent and deletion routes do not target the callback-created token principal; callers sharing the placeholder can modify or delete that placeholder's records. No production exposure or ownership of other rows is established. Resolve a stable authenticated principal, scope all relevant operations to it, and inventory every data location before promising complete erasure.

### COG-002 — Access token returned to callback caller
**Confirmed response behavior; conditional security risk / owner architecture decision.** [`auth.py:100–104`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/auth.py#L100-L104) assigns both access and refresh tokens to a database row; [`models.py:93–104`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/models.py#L93-L104) declares text fields. [`auth.py:119–123`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/auth.py#L119-L123) returns `"access_token": credentials.token`, not the refresh token. The requested scopes include calendar read and events ([`auth.py:20–24`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/auth.py#L20-L24)).

Returning a bearer credential expands the handling boundary; it is not itself proof of unauthorized disclosure. No client was inspected. Choose whether a trusted client needs it, minimize scopes and exposure, and verify the chosen response contract and storage controls. Encryption at rest, logs, access controls and retention are unknown.

### COG-003 — OAuth state is process-local and lacks visible expiry/session binding
**Medium; confirmed static, operational consequences conditional.** [`auth.py:26–27`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/auth.py#L26-L27) calls the dictionary an “In-memory state store”; [`:63–66`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/auth.py#L63-L66) stores a creation time, and [`:74–93`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/auth.py#L74-L93) checks membership and removes state **before** exchange, without visible expiry or initiating-session verification. Restart or cross-worker routing can invalidate a flow, depending on topology; unexpired unused entries persist in that process. Use a shared, expiring, session-bound store with atomic validation and consumption before exchange, and an explicit retry policy.

### COG-004 — Local configuration defaults need deployment review
**Confirmed defaults; deployed exposure and impact unverified.** [`config.py:9–20`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/config.py#L9-L20) defaults OAuth credentials to empty strings, `app_env` to development and `app_secret_key` to `change-me-in-production`. [`docker-compose.yml:22–28`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/docker-compose.yml#L22-L28) supplies the same secret fallback. These are local/default configuration values, not evidence that a real secret was exposed, a deployment uses them, or the stack boots. Secret consumption and real values are unknown. Validate required non-development configuration and isolate demo defaults.

### COG-005 — OAuth success claims consent without checking its record
**Confirmed static response; broader enforcement unverified.** The callback returns `"consent_granted": True` ([`auth.py:119–123`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/auth.py#L119-L123)); the inspected callback body does not query application consent ([`auth.py:74–117`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/routers/auth.py#L74-L117)). The separate model says “consent must be granted before data collection” ([`models.py:75–84`](https://github.com/knarayanareddy/cognition/blob/36241e5ab3dd49b6fd15b2eab88f7b684aeda4d7/backend/app/models.py#L75-L84)). OAuth provider authorization does not by itself establish the application's consent record. Determine the intended meaning and ensure the response and collection gates reflect an authenticated user's recorded choice; enforcement elsewhere was not inspected.

## Release blockers and owner decisions

Before real-user release, establish verified identity/ownership, truthful consent and scoped erasure; decide token handling, OAuth state store and deployment/secrets policy; verify tests, deployment, recovery and the actual frontend. Decide how legacy placeholder and orphaned token rows are handled without assigning them to an unverified person. Confirm required provider credentials, target environment, retention, restore objectives and operational ownership. Decisions inform the plan; existing owner authorization covers defensive documentation and does not require fresh consent per finding.
